# 架构：SLA 工具链的四段闭环

## 为什么是四段

SLA 是对外承诺，承诺要成立，背后必须有一条**闭合的证据链**：

```
      测得到 ──→ 查得清 ──→ 扛得住 ──→ 说得明
        ↑                                  │
        └────────── 反馈：容量与故障模式 ────┘
```

- **测得到**：知道「此刻能不能用」。没有它，后面三段没有输入。
- **查得清**：知道「坏了哪一层」。没有它，事故处理靠猜。
- **扛得住**：知道「还能撑多久」。没有它，只能等客户先发现变慢。
- **说得明**：能证明「上个月做到了多少」。没有它，承诺无法被验证，也就无法被信任。

四段缺一不可，但**顺序有依赖**：报表的数据来自巡检，巡检的判据来自诊断对故障模式的认识，
而诊断要在容量上压出问题才有素材。

## 第一段：测得到

### 判据

不是「`/health` 返回 200」，而是「**一个真实的客户端请求，从认证到响应体，完整走通**」。

这个判据来自实际踩过的坑：本项目经历过两次全链路 502，而 `/actuator/health` **始终是 UP**：

- 一次是实例落库时漏了 `adapter` 字段（#1004）——健康检查走 `socket_connect`，不经过适配器；
- 一次是 Netty 的 DNS 解析器不认识 compose 服务名（#1014）——健康检查走 glibc，转发走 Netty。

两次都是「健康检查说好，实际不能用」。所以巡检的核心必须是**合成事务**：
登录 → 选模型 → 发一次真实请求 → 校验响应体非空。

### 分项而不是汇总

依赖面分项探测：数据库、Redis（若启用）、每个上游模型、DNS。
每一项独立记录成败，不合并成一个 UP/DOWN。

理由：合并之后，一个上游挂了会把整组标红，运维看到 10 个红点，其中 9 个是同一个根因。
分项之后才能一眼看出「是这一个上游的问题」。

### 测点的位置

必须从**客户网络侧**发起，而不是从服务器自己看自己。
服务器自测通过而客户不通，最常见的原因是网络路径（DNS、代理、出站防火墙）。

## 第二段：查得清

### 分层诊断

本轮三个真实缺陷恰好落在三个不同的层，而任何单层探测都会漏掉另外两个：

| 层 | 缺陷 | 症状 | 哪一层能测出来 |
| --- | --- | --- | --- |
| 配置层 | 实例 `adapter` 为空（#1004） | 转发 502 | 读实例配置 |
| 解析层 | Netty 解析不了服务名（#1014） | `Failed to resolve` | 出站连通性 |
| 状态层 | 熔断器打开 / 复位接口对不上实例 id（#1009/#1010） | 503「all in circuit breaker state」 | 熔断器状态 |

所以 doctor 的设计是**五组检查并列**，而不是一个总分。

### 现场快照包（待建）

事故处理里最贵的成本是「来回问客户要信息」。快照包要一次收齐：

- 日志尾部（脱敏）、
- 运行态配置（从 API 读回的那份，不是磁盘上的）
- 指标快照、线程转储、连接池状态、
- 最近 N 条审计事件、
- 最近失败的若干个 requestId。

约束：**配置导出必须脱敏**，不能把 API Key、上游密钥写进包。

### requestId 追踪（待建）

现在的日志是分散的：入口、路由决策、上游调用、响应处理各写各的，没有一条公共 id。
补一条 trace id 贯穿即可，不需要重建日志体系。

## 第三段：扛得住

### 压测的正确问法

不是「能跑多少 RPS」，而是「**在客户的流量构成下**，p99 是多少、瓶颈在哪」。

已经踩过的教训：dev profile 的 DEBUG 日志会让基线从 370 RPS 掉到 97 RPS（见 #945）。
压测前必须把日志级别调到 WARN，否则测的是日志系统。

另一个教训：并发 100 时，连接池 10 与 32 的吞吐几乎一样（384.7 vs 368.6），
但 p99 从 1160ms 涨到 2552ms —— **吞吐看平均数会骗人，要看分位数**。

### 容量水位（待建）

输入：CPU、p99、连接池占用率、事件循环延迟。
输出：一句话 —— 「当前水位 65%，预计还能撑 1.8 倍流量」。

压测回答「峰值多高」，水位回答「下个月要不要扩容」。后者才是提前动作。

### 长稳测试（待建）

跑 24 小时，看内存、连接数、文件句柄、缓存条目数是否单调上升。
短时压测看不出泄漏 —— 本项目发现过 `Map` 无界增长、每个 SSE 连接做全表扫描这类问题，
都需要时间来暴露。

## 第四段：说得明

SLA 合同写「99.9%」很容易，**要能证明**才是服务。

- **可用性报表**：按客户、按周期，输出可用性百分比、错误预算消耗、TOP 故障类型。
  数据源是巡检记录，不是事后估算。
- **事件时间线导出**：事故复盘材料，也是客户沟通依据。
- **变更审计导出**：谁在何时改了什么配置。审计表已有，缺导出。

## 反馈环

报表里的「TOP 故障类型」和「容量水位」要能反过来指导前两段：
如果某类故障反复出现，说明巡检项不够；如果水位增长快于预期，说明压测场景要换。

这条反馈是四段之所以是**闭环**而不是流水线的原因。
